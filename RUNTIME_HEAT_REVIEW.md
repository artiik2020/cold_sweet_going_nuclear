Подробный журнал исправлений: [fixes.md](fixes.md)  
Учебное руководство и задачи SAM: [SAM.md](SAM.md)

## Итог аудита

Сама регистрация событий на `NeoForge.EVENT_BUS` была допустимой: `ServerTickEvent.Post` работает на логическом сервере, а `LevelTickEvent.Post` вызывается для каждого уровня и может быть клиентским или серверным. Код переведён на единый обработчик `LevelTickEvent.Post` с обязательной проверкой `ServerLevel`, чтобы отдельно обрабатывать каждое измерение.

Основные логические проблемы были в другом:

1. Кэш блоков в основном наполнялся событиями размещения. Старые реакторы и трубы, существующие при загрузке мира, могли не попасть в обработку.
2. Старый путь нагрева прибавлял значение к `Trait.WORLD` через `Temperature.add`. При повторных вызовах такое прибавление могло накапливаться, а не представлять устойчивый вклад отдельного источника.
3. Проверка Fluid Handler только в позиции трубы не гарантировала нахождение пара: у Create pipe может не быть собственного жидкостного инвентаря, а capability может принадлежать соседнему резервуару или машине.

## Текущее устройство

- `HeatTickHandler` — единая серверная точка входа. Периодически ищет блоки рядом с игроками и на каждом тике рассчитывает суммарное локальное воздействие.
- `PositionCache` — хранит кандидатов, найденных событиями размещения/разрушения и сканированием окрестности игроков. Сканирование не должно принудительно загружать чанки и ограничено радиусом 32 блока.
- `ReactorHandler` — вычисляет расстояние и вклад кандидатов реактора для конкретного игрока.
- `PipeHeatHandler` — вычисляет вклад труб с обнаруженным паром. Для удалённых труб capability не опрашивается до прохождения проверки расстояния.
- `SteamFluidHelper` — проверяет Fluid Handler в трубе и соседних блоках, а результат кэширует на интервал обновления. Он не расходует жидкость при обнаружении.
- `ColdSweatAdapter` — через reflection пытается использовать документированные методы `Temperature.get` и `Temperature.set` для `Trait.WORLD`. Он меняет отслеживаемый вклад, а не вызывает безусловный `add` с полной величиной на каждом тике.

## Единицы и ограничения

Cold Sweat описывает `WORLD` как окружающую температуру, которую испытывает конкретная сущность. Это не глобальная запись температуры биома и не изменение всех блоков в мире. Для этой версии адаптер задаёт bounded offset на игроке. Мировые температурные единицы Cold Sweat отличаются от градусов Цельсия; документация указывает приблизительный масштаб 1 MC unit = 23,3 °C. Значения конфигурации — вклады в этих единицах, не градусы Цельсия.

Публичная документация Cold Sweat:
- https://mikul.gitbook.io/cold-sweat/
- https://mikul.gitbook.io/cold-sweat/block-temperature

Для более нативного локального источника температуры можно изучить регистрацию `BlockTemp`, но в проект не добавлена обязательная compile-time зависимость Cold Sweat: это сделано намеренно, пока не проверены точная версия JAR и сигнатуры API. Не утверждается, что неизвестный `WorldTemperatureEvent` существует в установленной версии.

## Заглушки для дальнейшей разработки

В коде есть компилируемые TODO-заглушки:

- `ReactorHandler.isOperationalReactor(...)` пока возвращает `true`. После проверки исходников установленного Create: Going Nuclear нужно добавить реальный признак работы/нагрева.
- `SteamFluidHelper.inspectConnectedCreateNetwork(...)` пока возвращает `false`. Нужен подтверждённый API для обхода всей связанной сети Create. Проверки capability самой трубы и смежных инвентарей выполняются отдельно.

Подробные шаги выполнения задач приведены в `SAM.md`.

## Проверка

После получения обновлений локально:

```powershell
git pull origin master
.\\gradlew.bat compileJava
```

После сборки запустить игру с совместимыми версиями NeoForge, Cold Sweat, Create и Create: Going Nuclear. Проверить `/temperature get @s world` рядом с найденным реактором, сравнить температуру после выхода из радиуса и просмотреть сообщения логгеров `CSGN/HeatTickHandler`, `CSGN/ColdSweatBridge`, `CSGN/PositionCache` и `CSGN/SteamFluidHelper`.

**Статус проверки:** файлы обновлены в GitHub, но компиляция последней версии и поведение в реальном мире пока не подтверждены. Попытка получить репозиторий в окружение для сборки завершилась ошибкой DNS/сетевого доступа к GitHub, поэтому не следует считать проект проверенным без локального `compileJava` и игрового теста.


## Последнее обновление: runtime-конфигурация, диагностика паровых труб и экспериментальная конденсация

- Добавлено логирование действительных значений `SERVER` конфигурации при событии загрузки/перезагрузки; расчёты читают `.get()` во время выполнения.
- Дефолтные множители подняты до reactor 4.0, steam 1.5, общий предел 10.0 единиц Cold Sweat.
- Добавлена диагностика registry ID жидкостей и сообщения при обнаружении/применении нагрева от труб.
- Вспомогательный метод проверяет `FluidHandler.BLOCK` на трубе и непосредственных соседях; полного обхода сети Create пока нет.
- Добавлена опциональная конденсация для явно настроенного выходного блока. Она выключена по умолчанию и не должна использоваться на рабочем реакторном контуре без отдельного теста. Для водного блока необходимо 1000 mB пара; место выхода пока задаётся над блоком, ID выхода и orientation должны быть проверены пользователем.
- Добавлен CI workflow для `compileJava`, но доступного успешного результата последней сборки в этой сессии ещё нет.
