## 28 октября 2026 — интеграция нагрева и исправление компиляции

### 1. Почему изначально не работал нагрев

Во время проверки обнаружены несколько независимых проблем:

- Метод `ColdSweatAdapter.applyHeat(...)` был заглушкой и фактически не изменял температуру.
- Списки ID реакторов и труб в конфигурации по умолчанию были пустыми. Из-за этого блоки могли не попадать в кэш либо отсеиваться дополнительной проверкой.
- Проверка пара зависела от явно заданного ID жидкости, поэтому при пустой конфигурации не находила пар.
- Труба Create может не предоставлять Fluid Handler capability непосредственно на позиции блока трубы. В таком случае обычная проверка capability не позволяет прочитать содержимое всей сети труб.
- Реальная логика активности/нагрева реактора Going Nuclear пока не подтверждена по API конкретной версии мода.

### 2. Изменения в обработчике температуры

### 7. Исправление ошибки компиляции: `Iterable<ServerLevel>.stream()`

После предыдущих изменений пользователь получил две ошибки компиляции:

```
PipeHeatHandler.java:53: cannot find symbol
event.getServer().getAllLevels().stream()

ReactorHandler.java:49: cannot find symbol
event.getServer().getAllLevels().stream()
```

**Причина:** в используемой версии API `getAllLevels()` возвращает `Iterable<ServerLevel>`, а не Java Stream. У такого значения нет метода `.stream()`.

**Исправлено в файлах:**

- `src/main/java/com/yourname/myfirstmod/csgn/bridge/PipeHeatHandler.java`
- `src/main/java/com/yourname/myfirstmod/csgn/bridge/ReactorHandler.java`

Подсчёт кэшированных труб и реакторов заменён обычным циклом `for (ServerLevel level : event.getServer().getAllLevels())` с накоплением количества в целочисленную переменную. Так используется интерфейс `Iterable` напрямую, без вызова отсутствующего метода `.stream()`.

**Статус:** исправление отправлено в GitHub в ветку `master`. После получения обновлений необходимо повторно запустить `compileJava`, чтобы подтвердить, что две ошибки устранены.

### 8. Предупреждения компилятора

В выводе сборки также были предупреждения о deprecated API:

- `EventBusSubscriber.bus()` и `EventBusSubscriber.Bus` в `Csgn.java`, строка 122.
- Использование устаревшего API в `BridgeConfig.java`.

Это **предупреждения, а не причины текущего провала компиляции**: сборка остановилась из-за двух ошибок `.stream()`. Их можно отдельно обновить под API установленной версии NeoForge после подтверждения актуального способа регистрации клиентских обработчиков и конфигурации. Без проверки не следует механически менять регистрацию событий, поскольку можно нарушить разделение клиентского и общего кода.

### 9. Регистрация событий

Обработчики серверного тика используют `ServerTickEvent.Post` и регистрируются на `NeoForge.EVENT_BUS`. Для игровых событий тика это правильная шина; перенос обработчиков на mod event bus не устранил бы пустую реализацию адаптера температуры.

## 28 октября 2026 — повторный аудит событий, обнаружения блоков и температуры

### Основные выводы аудита

1. **Подписка на серверный тик сама по себе была корректной.** Ранее `ReactorHandler` и `PipeHeatHandler` регистрировались на `NeoForge.EVENT_BUS`, где NeoForge публикует `ServerTickEvent.Post`. Причина отсутствия нагрева не сводилась к неправильной шине событий.
2. **Кэш не находил старые источники автоматически.** Он в основном заполнялся при размещении блоков после запуска мода. Реактор, уже построенный к моменту загрузки мира, мог не попасть в обработчик.
3. **Повторное использование `Temperature.add(..., WORLD, strength)` было логически опасным.** Метод добавляет значение к WORLD-признаку конкретной сущности. Регулярное добавление полного значения без компенсации старого смещения может накапливать температуру.
4. **Capability трубы и Fluid Handler инвентаря — не обязательно одно и то же.** Create использует трубы для переноса жидкости, а жидкость может находиться в подключённом резервуаре или машине. Поэтому проверка только capability в самой трубе недостаточна.
5. В публичной документации Cold Sweat подтверждены `Temperature.get(LivingEntity, Trait)`, `set(LivingEntity, Trait, double)`, `add(LivingEntity, Trait, double)`, а `WORLD` описан как окружающая температура, которую испытывает сущность. Эти вызовы работают с признаком конкретного существа, а не изменяют глобально температуру биома. Документация также указывает, что мировая температура Cold Sweat использует Minecraft-единицы; одна единица приблизительно равна 23,3 °C. Ссылки: [основы API Cold Sweat](https://mikul.gitbook.io/cold-sweat/) и [Block Temperature](https://mikul.gitbook.io/cold-sweat/block-temperature).

После запуска проверь конфигурацию мода: радиус реактора должен быть не больше 32, начальное значение — 16; вклад реактора по умолчанию — 0.20, пара — 0.10. Если в конфиге остались прежние значения, обнови их вручную и перезапусти мир/сервер.

## 28 октября 2026 — настройки во время выполнения, усиление нагрева и диагностика пара

### Конфигурация и интенсивность

Причина кажущегося игнорирования настроек могла быть в двух местах: текущий мир использует конфигурацию типа `SERVER`, а общий предел нагрева раньше был жёстко задан значением `0.75`. Даже увеличение множителя не могло превысить этот предел.

В `bridge/BridgeConfig.java` теперь заданы значения по умолчанию: `reactorHeatMultiplier = 4.0`, `steamHeatMultiplier = 1.5`, `maxTotalHeat = 10.0`; радиус реактора — 16 блоков, трубы — 8 блоков. Обработчики продолжают читать значения через `.get()` во время расчёта. Добавлен слушатель `ModConfigEvent`, который пишет в INFO реальные значения активной конфигурации и списки ID. `HeatTickHandler` теперь использует конфигурируемый `MAX_TOTAL_HEAT` вместо жёсткого ограничения 0.75. В `ReactorHandler` добавлен лог радиуса и множителя при обнаружении реактора.

Для одиночного мира конфиг типа `SERVER` обычно находится в `.minecraft/saves/<имя_мира>/serverconfig/csgn-server.toml`, а не в корневом `.minecraft/config`. При изменении настроек ориентируйся на значения в INFO сообщении, а не только на то, что записано в предполагаемом файле.

### Диагностика и распознавание пара

В `bridge/SteamFluidHelper.java` остался правильный для жидкостей тип capability — `Capabilities.FluidHandler.BLOCK`. `ItemHandler` предназначен для предметных слотов, не для жидкостей. Теперь helper проверяет capability самой трубы и шести соседних блоков; впервые встреченные ID жидкостей видны в INFO логе. При пустом списке `steamFluidIds` принимаются лишь ID с namespace, похожим на Going Nuclear, и путём, содержащим `steam`. Если список заполнен, он является точным белым списком. Если ни труба, ни соседние блоки не предоставляют Fluid Handler, лог сообщает об этом и указывает на пока не реализованный обход сети Create.

В `PipeHeatHandler.java` добавлен INFO лог «Труба найдена, пар есть, применяю тепло» с радиусом, множителем, расстоянием и игроком. Он не выводится каждую игровую итерацию для одной и той же трубы.

### Конденсация: ограниченная и опциональная

Добавлен `enableCondensation` (по умолчанию `false`) и список точных ID выходных блоков `condensationOutputBlockIds`. Метод конденсации запускается только для трубы, рядом с которой стоит явно настроенный выход и найден пар. Проверяется свободная ячейка над выходным блоком, симулируется drain 1000 mB, затем выполняется реальный слив и устанавливается блок воды; при неудаче размещения выполняется попытка вернуть жидкость. Повторный слив в ячейку, уже содержащую жидкость, предотвращён.

**Ограничение:** полный обход Fluid Network Create не реализован; источник пара должен быть доступен через Fluid Handler самой трубы или непосредственного соседа. Заглушка `inspectConnectedCreateNetwork(...)` с комментарием `TODO: Artem's Task` возвращает `false`, пока не подтверждён публичный API конкретной версии Create. ID выходного блока и направление выхода не выдумывались: список пуст по умолчанию, вода ставится над явно настроенным выходом. В документации Going Nuclear уже описан собственный Radiator, конденсирующий пар при работе с Encased Fan, поэтому не следует включать самописный слив на штатном радиаторе без теста — можно нарушить работу турбин/контура.

### Дополнение: кэш также сбрасывается при перезагрузке конфигурации

После события `ModConfigEvent` вызывается очистка кэша определения пара в `SteamFluidHelper.clearCache()`, а также сбрасываются одноразовые логи труб и реакторов. Файл `.github/workflows/gradle-build.yml` исправлен: GitHub Actions самостоятельно устанавливает Gradle 8.14 и запускает `gradle --no-daemon compileJava`.
