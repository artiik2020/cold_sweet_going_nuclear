## 1. Как читать Java-файл

Читайте исходник сверху вниз в таком порядке:

1. **`package`** — пакет, то есть логическое расположение класса в проекте.
2. **`import`** — классы и интерфейсы, которые используются в этом файле.
3. **Объявление класса** — например, `public final class ReactorHandler`.
4. **Поля класса** — состояние, константы, логгеры и счётчики.
5. **Конструктор** — способ создания объекта. У класса-обработчика может быть закрытый конструктор, если все методы статические.
6. **Основные методы** — входные точки, вызываемые событиями, и порядок действий.
7. **Вспомогательные методы** — небольшие операции, вынесенные отдельно для ясности.

Не пытайтесь сразу запомнить каждую строку. Сначала ответьте на вопросы: кто вызывает этот класс, какие данные он получает, что он меняет и как сообщить об ошибке?

## 2. Важные конструкции Java, встречающиеся в проекте

### Переменные и типы

```java
int count = 0;
double radius = 8.0;
boolean found = false;
```

- `int` — целое число.
- `double` — число с дробной частью.
- `boolean` — `true` или `false`.
- Имя переменной должно объяснять назначение значения: `cachedPipeCount) лучше, чем `x`.

### Условия

```java
if (event.getServer() == null) {
    return;
}
```

Если сервера нет, метод завершает работу. Это ранняя проверка, которая помогает не выполнять код с недопустимыми данными.

### Цикл по Iterable

```java
int count = 0;
for (ServerLevel level : server.getAllLevels()) {
    count += PositionCache.reactors(level).size();
}
```

`getAllLevels()` в используемом API возвращает `Iterable<ServerLevel>`. Интерфейс `Iterable` поддерживает цикл `for-each`, но не предоставляет метод `.stream()`. Поэтому такой цикл совместим с возвращаемым типом без преобразований.

### Коллекции

- `List<BlockPos>` — список позиций блоков.
- `add(position)` — добавить элемент.
- `removeAll(stale)` — удалить все элементы, перечисленные в другой коллекции.
- `size()` — получить число элементов.

Перед изменением коллекции, по которой идёт обход, подумайте, не приведёт ли это к ошибкам итерации. В обработчиках проекта устаревшие позиции сначала складываются в отдельный список, а удаляются после обхода.

### Методы и аргументы

```java
ColdSweatAdapter.applyWorldHeat(level, player, desiredOffset);
```

Это вызов метода `applyWorldHeat`. В него передаются серверный уровень, игрок и итоговое целевое смещение в единицах температуры Cold Sweat. Расчёт вклада реактора и труб выполняется в `ReactorHandler`, `PipeHeatHandler` и `HeatTickHandler`.

### Логирование

```java
LOGGER.debug("Cached reactor positions={}", cachedReactorCount);
```

Лог помогает увидеть внутреннее состояние программы. Уровень `DEBUG` может быть скрыт в обычной конфигурации логирования, поэтому отсутствие строки в логе не всегда означает, что код не выполнялся.

## 3. Как устроен путь нагрева в этом проекте

Общая логика состоит из нескольких шагов:

1. **Обнаружение блока.** `PositionCache` отслеживает подходящие блоки и хранит их позиции.
2. **Обработка серверного тика.** `ReactorHandler` и `PipeHeatHandler` периодически обходят сохранённые позиции.
3. **Проверка позиции.** Обработчик убеждается, что блок ещё загружен и его состояние подходит под критерии.
4. **Проверка пара.** Для труб `SteamFluidHelper` пытается определить жидкость через Fluid Handler capability.
5. **Поиск игроков поблизости.** Обработчик проверяет расстояние от игрока до источника.
6. **Изменение температуры.** `ColdSweatAdapter` пытается передать изменение в API Cold Sweat.
7. **Диагностика.** Логгеры помогают определить, на каком шаге процесс остановился.

Важно: наличие блока в кэше ещё не доказывает, что он активен или горячий. Эвристическое распознавание ID — только способ найти кандидата; для реальной интеграции может потребоваться проверка состояния из API самого мода.

## 4. Как понять проверку расстояния

В обработчиках используется сравнение квадрата расстояния:

```java
double radiusSquared = radius * radius;
if (player.distanceToSqr(x, y, z) > radiusSquared) {
    continue;
}
```

`distanceToSqr` возвращает квадрат расстояния, поэтому квадрат радиуса сравнивается с ним напрямую. Это позволяет не вычислять квадратный корень для каждого игрока. Если расстояние больше радиуса, `continue` пропускает этого игрока и цикл переходит к следующему.

## 5. Как разбирать ошибку компиляции

Когда Gradle сообщает об ошибке:

1. Найдите **первую строку с `error:`**. Предупреждения `warning:` обычно не останавливают сборку сами по себе.
2. Запишите файл и номер строки.
3. Прочитайте сообщение после `error:`.
4. Найдите тип выражения слева и посмотрите, какие методы доступны у этого типа в версии API проекта.
5. Исправьте первопричину, а не просто скрывайте сообщение.
6. Запустите сборку повторно и проверьте весь вывод, поскольку после первой ошибки могут проявиться следующие.

### Пример из этого проекта: `.stream()`

Ошибка:

```text
cannot find symbol: method stream()
location: interface Iterable<ServerLevel>
```

Она означает, что компилятор знает тип выражения — `Iterable<ServerLevel>` — и не находит у него метод `stream()`. Исправление — обход через `for (ServerLevel level : ...)`, а не попытка вызвать отсутствующий метод.

Команда проверки из PowerShell в корне проекта:

```powershell
.\gradlew.bat compileJava
```

Чтобы получить более подробный вывод:

```powershell
.\gradlew.bat compileJava --warning-mode all
```

Предупреждения об устаревшем API нужно разбирать отдельно. Не меняйте регистрацию событий наугад: для NeoForge важны правильная шина событий и разделение клиентского и серверного кода.

## 6. Как безопасно вносить собственные изменения

Перед правкой:

- Прочитайте весь метод, а не только строку с проблемой.
- Найдите все места, откуда вызывается изменяемый метод.
- Проверьте, какие типы и значения передаются в аргументах.
- Уточните, выполняется ли код на клиенте или сервере.
- Проверьте, может ли значение быть `null`.
- Подумайте, не будет ли метод вызываться каждый тик и не создаёт ли он дорогой обход мира.
- Сохраняйте диагностические сообщения для важных веток, но не спамьте логом каждый тик без необходимости.

После правки:

1. Запустите `compileJava`.
2. Если сборка успешна — проверьте соответствующую механику в игре.
3. Если это логика тиков, проверьте её при нескольких состояниях: блок есть, блока нет, игрок далеко, игрок рядом.
4. Посмотрите лог и убедитесь, что он подтверждает ожидаемый путь выполнения.
5. Запишите в `fixes.md` причину, изменённые файлы и результаты проверки.
6. Обновите этот `SAM.md`, если появилась новая конструкция, важная особенность API или урок из ошибки.

## 7. Как добавлять функции в обработчики

Старайтесь держать один метод ответственным за одну понятную задачу. Например:

- поиск подходящих блоков — в кэше;
- проверка жидкости — в `SteamFluidHelper`;
- выбор игроков в радиусе — в обработчике;
- вызов API температуры — в `ColdSweatAdapter`.

Так проще проверить каждую часть отдельно. Не копируйте одну и ту же сложную логику в несколько классов: если поведение общее, рассмотрите небольшой вспомогательный метод или отдельный класс.

Не добавляйте выдуманные имена методов из стороннего мода. Сначала проверьте исходный код, документацию или содержимое JAR именно той версии, которая используется проектом.

## 10. Аудит нагрева: почему обработчик может вызываться, но эффекта не видно

### Подписка на событие

Теперь `Csgn` регистрирует один общий обработчик:

```java
NeoForge.EVENT_BUS.addListener(HeatTickHandler::onLevelTick);
```

Метод принимает `LevelTickEvent.Post`. Это событие вызывается после обработки каждого игрового тика уровня и может приходить как для клиента, так и для сервера. Поэтому первая проверка в обработчике:

```java
if (!(event.getLevel() instanceof ServerLevel level)) {
    return;
}
```

Она не позволяет изменять температуру на клиенте. `NeoForge.EVENT_BUS` — правильная шина для этих игровых событий. Проблема была не в том, что обработчики обязательно не вызывались: прежняя регистрация `ServerTickEvent.Post` тоже была допустимой. Куда важнее, что в старой схеме кэш не находил уже стоящие в мире блоки, если они не были размещены после старта мода.

### Почему кэша недостаточно

`PositionCache` продолжает слушать события размещения и удаления блоков. Но новый метод `scanNear` дополнительно осматривает ограниченную область вокруг игроков по таймеру. Так старый реактор или труба, уже существовавшие при загрузке мира, попадут в кэш, когда игрок приблизится.

Сканирование не загружает незагруженные чанки намеренно. Радиус ограничен 32 блоками, чтобы не запускать огромный перебор куба при каждом тике. По умолчанию радиус реактора теперь 16 блоков.

### Почему нельзя просто постоянно вызывать `Temperature.add`

`Temperature.add(entity, Trait.WORLD, amount)` прибавляет значение к температурному признаку сущности. Если каждый раз добавлять полное значение, оно может накапливаться и уходить далеко от исходного значения.

Теперь `HeatTickHandler` суммирует влияние источников на конкретного игрока, ограничивает общую прибавку и передаёт целевое смещение в `ColdSweatAdapter.applyWorldHeat`. Адаптер использует документированные методы `Temperature.get/set` через reflection: он заменяет собственное предыдущее смещение, а не прибавляет его заново. Если Cold Sweat пересчитал WORLD между вызовами, адаптер повторно применяет смещение к новому значению.

**Важно:** `Trait.WORLD` — окружающая температура, которую испытывает конкретная сущность. Это не изменение глобальной температуры биома или всех блоков мира. Для настоящего источника локальной температуры в модели Cold Sweat предназначен API `BlockTemp`; прямое изменение `WORLD` выбрано как ограниченный вариант без обязательной зависимости проекта от jar Cold Sweat.

### Что значит величина нагрева

Cold Sweat использует собственные Minecraft-единицы для мировой температуры. Документация Cold Sweat указывает, что одна такая единица приблизительно равна 23,3 °C. Поэтому `0.20` — это прибавка 0,20 единицы температуры мира, а не 0,20 °C. Эффект плавно уменьшается по мере удаления от источника.

### Работа с трубами Create

У Fluid Handler capability может не быть отдельного инвентаря в самом блоке трубы: Create транспортирует жидкость по сети, а содержимое обычно хранится в подключённом инвентаре. `SteamFluidHelper` поэтому проверяет capability в позиции трубы и на соседних блоках со стороны, обращённой к трубе. Результат кэшируется на интервал обновления, чтобы не запрашивать capability каждого сегмента трубы на каждом игровом тике.

Заглушка `inspectConnectedCreateNetwork` намеренно возвращает `false`. Это не ошибка компиляции: она обозначает место для будущей полноценной интеграции с сетью Create. До проверки API установленной версии мода нельзя выдумывать название класса сети или метод получения жидкости.

## 11. Задачи SAM: продолжение разработки

В коде оставлены заглушки с пометками `TODO: Artem's Task`. Они имеют безопасные реализации по умолчанию, поэтому мод должен компилироваться без дописывания этих методов.

### Задача A — определять, включён ли реактор

Файл: `bridge/ReactorHandler.java`, метод `isOperationalReactor`.

Сейчас метод возвращает `true` для распознанного блока: это позволяет проверить основной путь нагрева, но может нагревать рядом даже с выключенным реактором.

Порядок работы:

1. Узнай точный ID и версию Create: Going Nuclear из своего набора модов.
2. Посмотри исходники соответствующего релиза или декомпилируй JAR и найди Block/BlockEntity реактора.
3. Найди реальное свойство или метод, который означает «реактор работает» или «реактор горячий».
4. Только после проверки добавь типизированную проверку в этот метод. Не придумывай имена вроде `isActive()`, пока не увидел их в исходниках.
5. Для состояния «выключен» метод должен вернуть `false`; при сомнительных или отсутствующих данных лучше временно оставить прежнее безопасное поведение и написать об ограничении.

### Задача B — читать жидкость из всей сети Create

Файл: `bridge/SteamFluidHelper.java`, метод `inspectConnectedCreateNetwork`.

Сейчас метод возвращает `false`, но проверка capability самой трубы и соседних блоков уже работает. Полный обход сети зависит от внутреннего API Create и его версии.

1. Уточни точную версию Create.
2. Изучи исходники Fluid Pipe, Smart Fluid Pipe, Fluid Valve и соединённых резервуаров в этой версии.
3. Установи, где фактически доступен `IFluidHandler`, и есть ли публичный способ пройти по соединённой сети.
4. Реализуй обход только после того, как типы и методы подтверждены в исходниках.
5. Ограничь максимальное количество посещаемых узлов и не загружай чанки принудительно.
6. Пока заглушка возвращает `false`, она не ломает соседнюю проверку capability.

### Задача C — перейти к штатным источникам температуры Cold Sweat

Файл: `bridge/ColdSweatAdapter.java`.

Текущая реализация воздействует на `WORLD` конкретного игрока, а не на глобальный мир. Если для финальной архитектуры нужна полноценная локальная температура блока, проверь API `BlockTemp` и событие регистрации `BlockTempRegisterEvent` конкретной версии Cold Sweat.

Не добавляй прямые импорты из Cold Sweat вслепую: проект сейчас специально не требует Cold Sweat как compile-time зависимости, чтобы исходники могли собираться в dev-среде без его API jar. Перед изменением зависимости необходимо проверить точную версию, координаты артефакта и сигнатуры в источниках установленного релиза.

## 12. Пошаговое создание Java-класса, блока и предмета

### Создание обычного класса

1. В IntelliJ IDEA щёлкни правой кнопкой по пакету `com.yourname.myfirstmod.csgn` или нужному подпакету.
2. Выбери **New → Java Class** и дай классу имя, например `MyHelper`.
3. Убедись, что строка `package` совпадает с папкой.
4. Начни с простого метода и проверь типы аргументов и результата.

Пример простого вспомогательного класса:

```java
package com.yourname.myfirstmod.csgn;

public final class MyHelper {
    private MyHelper() {
    }

    public static boolean isPositive(int value) {
        return value > 0;
    }
}
```

В Java тип указывается явно. В отличие от Python, `int` и `boolean` — часть объявления метода и должны совпадать с возвращаемым значением. `static` означает, что метод принадлежит классу и его можно вызвать без создания объекта: `MyHelper.isPositive(5)`.

### Регистрация простого блока

В проекте уже есть образец `EXAMPLE_BLOCK` в классе `Csgn`. Для нового блока обычно требуются объект блока и, если игрок должен получать его в инвентарь, предмет-блок (`BlockItem`):

```java
public static final DeferredBlock<Block> MY_BLOCK =
    BLOCKS.registerSimpleBlock("my_block",
        BlockBehaviour.Properties.of().mapColor(MapColor.STONE));

public static final DeferredItem<BlockItem> MY_BLOCK_ITEM =
    ITEMS.registerSimpleBlockItem("my_block", MY_BLOCK);
```

Это образец структуры регистрации: импортируй нужные типы из Minecraft/NeoForge, расположи поля внутри `Csgn` и используй уникальное имя. ID блока будет `csgn:my_block`, а ID предмета — `csgn:my_block`.

### Регистрация обычного предмета

```java
public static final DeferredItem<Item> MY_ITEM =
    ITEMS.registerSimpleItem("my_item", new Item.Properties());
```

Этот предмет получит ID `csgn:my_item`. Чтобы положить его в творческую вкладку, добавь его в `displayItems` соответствующей вкладки или используй событие `BuildCreativeModeTabContentsEvent`.

### Подключение реестров

Регистры необходимо привязать к mod event bus в конструкторе `Csgn`:

```java
BLOCKS.register(modEventBus);
ITEMS.register(modEventBus);
```

В текущем проекте это уже сделано. Если добавляешь только новые поля в существующие `BLOCKS` и `ITEMS`, повторно регистрировать эти регистры не нужно.

### Регистрация игрового обработчика

Для общего серверного игрового события в текущем проекте используется шина событий NeoForge:

```java
NeoForge.EVENT_BUS.addListener(HeatTickHandler::onLevelTick);
```

Метод должен принимать соответствующий тип события. Для `LevelTickEvent.Post` сначала проверь, что уровень является `ServerLevel`, потому что событие также бывает клиентским. Для событий жизненного цикла/регистрации содержимого используй mod event bus, который передаётся в конструктор `Csgn`. Не смешивай эти две шины.

### Дополнение: предупреждение про `EventBusSubscriber.bus()`

В NeoForge 1.21.1 параметр `bus = EventBusSubscriber.Bus.MOD` устарел и помечен для удаления. В `Csgn.ClientModEvents` он убран, чтобы компилятор не показывал предупреждение. Тип события `FMLClientSetupEvent` позволяет NeoForge выбрать mod event bus автоматически. Для обработчика игрового `LevelTickEvent.Post` по-прежнему используется явная подписка на `NeoForge.EVENT_BUS`.

## 13. Последние изменения: настройка температуры, трубы и конденсация

### Почему конфигурация может казаться «неактивной»

Обработчики читают значения через `BridgeConfig.SOME_VALUE.get()` при расчёте, а не копируют их в статические числа во время старта. Например, радиус и множитель нагрева считываются в `ReactorHandler.heatForPlayer`, а общий предел — в `HeatTickHandler`. При изменении конфигурации `ModConfigEvent` пишет актуальные значения в журнал.

Особенность этого проекта: `BridgeConfig.SPEC` зарегистрирован как конфигурация типа `SERVER`. Поэтому для одиночного мира проверь именно файл:

```text
.minecraft/saves/<имя_мира>/serverconfig/csgn-server.toml
```

На выделенном сервере ищи серверную конфигурацию в `serverconfig` каталоге мира. Не редактируй наугад одноимённый файл в корневом каталоге `.minecraft/config`: он может не быть активным файлом типа SERVER для данного мира.

При загрузке или перезагрузке в логе должна быть строка с `Bridge config SERVER` и фактическими значениями `reactor radius`, `reactor heat`, `pipe radius`, `steam heat` и `max total heat`. Если там старые числа, ты редактируешь не тот файл или конфигурация не перезагрузилась.

### Как читать множители

Множители задаются в единицах температуры Cold Sweat, а не в градусах Цельсия. В конфигурации используются три разных значения:

- `reactorHeatMultiplier` — максимальный вклад одного распознанного реактора вблизи блока.
- `steamHeatMultiplier` — максимальный вклад обнаруженной паровой трубы.
- `maxTotalHeat` — предел для суммарного вклада всех обнаруженных источников.

Вклад плавно уменьшается с расстоянием. Если `maxTotalHeat` меньше вклада реактора, итог обрезается этим пределом. Поэтому при тестировании интенсивности не забудь проверить сразу все три значения. Текущие значения по умолчанию усилены, но не следует ставить очень большие числа без игрового теста.

### Как правильно искать жидкость

В NeoForge 1.21.1:

- `Capabilities.FluidHandler.BLOCK` используется для жидкостных инвентарей блоков.
- `Capabilities.ItemHandler.BLOCK` предназначен для инвентарей предметов, а не для жидкостей.
- `Capabilities.FluidHandler.ITEM` нужен для жидкостного содержимого предметов, например переносного контейнера. Он не является заменой API сети труб.

Труба Create может только транспортировать жидкость и не обязана отдавать `IFluidHandler` на своей позиции. В текущей версии помощник проверяет Fluid Handler на трубе и у шести соседей. В лог записывается ID впервые встреченной жидкости и факт, распознана ли она как пар Going Nuclear.

Когда список `steamFluidIds` пуст, запасная проверка принимает только жидкости, у которых namespace похож на Going Nuclear и путь содержит `steam`. Точный ID намеренно не выдумывается. Если лог показывает реальный ID жидкости, который должен считаться паром, добавь его в `steamFluidIds` через список с полным registry ID, например `namespace:path` из лога. При непустом списке именно он становится белым списком допустимого пара.

Если в логах написано, что у трубы и соседних блоков нет Fluid Handler, значит проверка capability не может видеть жидкость сети через эти позиции. В `SteamFluidHelper.inspectConnectedCreateNetwork` есть:

`// TODO: Artem's Task - Implement Create fluid-network traversal ...`

Для этой задачи необходимо изучить исходники конкретной установленной версии Create и найти публичный способ чтения содержимого Fluid Network. Не придумывай имена классов/методов заранее и не заменяй Fluid Handler на Item Handler.

### Как устроена конденсация сейчас

В официальном описании Create: Going Nuclear есть собственный Radiator, который превращает пар обратно в воду при работе с Encased Fan, а также Steam Vent, выпускающий лишний пар в воздух. Поэтому нельзя автоматически сливать жидкость из каждой трубы: так можно сломать турбину или нормальный цикл реактора.

В мосте добавлен **экспериментальный, отключённый по умолчанию** путь конденсации. Чтобы включить его осознанно:

1. Сначала получи настоящий registry ID тестируемого выходного блока из установленной версии Going Nuclear. Не подставляй предполагаемый ID.
2. В `enableCondensation` укажи `true`.
3. В `condensationOutputBlockIds` добавь только проверенный ID выходного блока.
4. В тестовом мире поставь выходной блок рядом с сегментом трубы, у которого реально доступен Fluid Handler с паром.
5. Убедись, что блок над выходом пустой и незанятый жидкостью.
6. Посмотри лог: при успехе будет строка `Пар сконденсирован в воду`.

Текущая реализация сначала симулирует слив, требует полную порцию 1000 mB, затем выполняет слив и устанавливает блок воды над отмеченным выходом. Если размещение воды не удаётся, она пытается вернуть слитую жидкость в исходный handler. Повторная конденсация в уже занятую жидкостью ячейку предотвращается.

**Ограничение:** полный Create Fluid Network обход пока не реализован. Конденсация может работать только тогда, когда обработчик жидкости доступен на самой трубе или у непосредственно соседнего блока. Для трубопровода, в котором источник жидкости дальше по сети, остаётся задача Artem. Направление выпуска воды временно задано как «над выходным блоком»; это надо сверить с ориентацией конкретного радиатора/вентиля. Не включай экспериментальную конденсацию на рабочем реакторе до теста.

### Как тестировать последние изменения

1. Обнови ветку `master` и выполни `.\gradlew.bat compileJava`.
2. Запусти игру с логированием уровня INFO.
3. Открой правильный `serverconfig/csgn-server.toml`, поменяй `reactorHeatMultiplier` и `maxTotalHeat`, затем перезагрузи конфигурацию/мир.
4. Убедись, что лог показывает изменённые значения.
5. Проверь источник реактора: в логе должно появиться `Реактор найден, читаю конфиг: radius=...`.
6. Для трубы проверь строки `FluidHandler увидел жидкость`, `Труба найдена, пар есть` и `применяю тепло`. Если namespace или путь жидкости не прошёл фильтр, настрой точный `steamFluidIds`.
7. Тест конденсации проводи отдельно, только с тестовым выходом и включённым `enableCondensation`.

Все новые тесты нужно записать в `fixes.md`: отдельно успешную компиляцию, проверку нагрева в игре, обнаружение ID пара и реальный тест конденсации. Не отмечай тест выполненным только потому, что исходник был изменён.

## 14. Последние изменения: конфигурация, паровые трубы и конденсация

### Как понять, что конфигурация реально прочитана

`BridgeConfig` зарегистрирован как конфигурация типа `SERVER`. Для одиночного мира проверь файл `.minecraft/saves/<имя_мира>/serverconfig/csgn-server.toml`. Обработчики читают `BridgeConfig.*.get()` при расчёте, а слушатель `ModConfigEvent` пишет в INFO реальные значения после загрузки/перезагрузки. Если меняешь файл, но INFO сообщает прежние числа, проверь путь и перезагрузку.

Вкладов три: `reactorHeatMultiplier` (реактор), `steamHeatMultiplier` (пар) и `maxTotalHeat` (предел их суммы). Поэтому повышение множителя не даст эффекта выше `maxTotalHeat`. Текущие значения по умолчанию: 4.0, 1.5 и 10.0 единиц Cold Sweat соответственно. Единицы Cold Sweat — не градусы Цельсия.

### Как читать сообщения трубы

- `FluidHandler увидел жидкость: id=...` — лог показывает настоящий registry ID жидкости и решение фильтра.
- `Труба найдена, пар есть` — жидкость распознана как steam.
- `Труба найдена, пар есть, применяю тепло` — труба находится в радиусе игрока и её вклад добавлен в расчёт.
- Сообщение об отсутствии FluidHandler — труба и соседние блоки не предоставили жидкостную capability; нужен подтверждённый способ обхода сети Create.
- `Пар сконденсирован в воду` — успешный drain и установка водного блока.

Для жидкости используй `Capabilities.FluidHandler.BLOCK`. `Capabilities.ItemHandler.BLOCK` читает слоты предметов и не заменяет Fluid Handler. В случае, когда список `steamFluidIds` пуст, запасная проверка требует namespace, похожий на Going Nuclear, и путь с `steam`. Если в логе появляется настоящий steam ID, но он не распознаётся, добавь полный ID в список. Непустой список работает как строгий белый список, поэтому внеси все нужные варианты пара.

### Конденсация — только явный выход и безопасный тест

Конденсация выключена по умолчанию. Чтобы запустить тест, нужно включить `enableCondensation`, внести проверенный registry ID выходного блока в `condensationOutputBlockIds`, подвести выход к паровой трубе, у которой сама труба или соседний блок имеет Fluid Handler с не менее чем 1000 mB пара, и освободить ячейку над выходом. Код сначала симулирует drain, затем сливает 1000 mB и ставит воду; при ошибке размещения пытается вернуть жидкость. Вода ставится над выходным блоком, так как реальное направление конкретного выхода не подтверждено.

**Не включай этот эксперимент на рабочем реакторе до проверки.** Going Nuclear уже содержит собственный Radiator, который конденсирует пар при работе с Encased Fan. Не следует автоматически дренировать каждую трубу: это может сломать поток к турбине. Полный обход Fluid Network Create остаётся `TODO: Artem's Task` в `SteamFluidHelper.inspectConnectedCreateNetwork` и безопасно возвращает `false`, пока не подтверждён публичный API конкретной версии Create.

4. Проверь лог реактора, затем ID жидкости и лог применения тепла от трубы.
5. Конденсацию проверяй только в отдельном тестовом мире и отмечай результат в `fixes.md`.

### Важное дополнение о перезагрузке конфигурации

При событии `ModConfigEvent` кэш жидкости очищается через `SteamFluidHelper.clearCache()`, а одноразовые сообщения обработчиков сбрасываются. Это нужно, чтобы новая настройка `steamFluidIds` сразу пересчитала предыдущие отрицательные результаты и повторно показала диагностические строки. После изменения файла ищи в журнале `Bridge config SERVER` с актуальными числами.

В локальном окружении проекта у тебя может быть `gradlew.bat`, но на GitHub wrapper-файлы не добавлены. Поэтому текущий GitHub Actions workflow устанавливает Gradle 8.14 отдельно и запускает `gradle --no-daemon compileJava`.
